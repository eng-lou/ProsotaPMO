## Session 5 — 2026-07-01 (continued): A real bug, found by actually trying it

Maro tried the Risk Register in a real browser as suggested, and hit an error: "Failed to create project." This turned out to be a genuine bug, and a good example of why the "click through it yourself" step matters — all the automated checks in Session 4 had passed, but they couldn't have caught this.

1. **What actually broke.** The backend uses a database driver (something that lets the Python code talk to PostgreSQL) that, on Windows specifically, needs a particular kind of "event loop" (the underlying machinery that lets the program do several things at once) called a `SelectorEventLoop`. Windows normally defaults to a different one. The automated tests already had a workaround for this, but the real running server didn't — and nobody had noticed, because every check so far had only touched a trivial "are you alive?" endpoint that doesn't use the database at all. The moment a real feature tried to write to the database, it broke.
2. **How it was found.** By reading the backend's own error log after the failure — the real cause was clearly written there, several layers down in a technical stack trace, even though the app only showed the user a generic "Failed to create project" message.
3. **How it was fixed.** Added a small new file, `backend/run.py`, whose only job is to tell Windows to use the correct event loop *before* the server starts up. From now on, the backend should be started with `python run.py` instead of the raw `uvicorn` command.
4. **Checked before declaring it fixed.** Ran a direct, isolated database query using the same fix to prove the connection genuinely worked, before asking Maro to try again in the browser rather than just assuming it was fixed.
5. **Confirmed working, then committed.** Maro retried creating a project in the real browser and confirmed it worked. Only then were the Risk Register feature and this bug fix saved to git together.

End of session 5: Risk Register works end-to-end, confirmed by an actual human clicking through it, not just automated checks. This is now the standing rule for every future session too: build it, check what can be checked automatically, but never mark something "done" or commit it until a human has actually confirmed the real thing works.

## Session 8 — 2026-07-01 (continued): Learning to get the project-management maths right

After confirming the previous round of fixes worked, Maro made a bigger-picture point: as a real project-management expert, he'd noticed a pattern — the CPI/SPI mistake earlier, and now the same kind of mistake in something called "EMV" (Expected Monetary Value, a standard way of estimating how much a risk is really "worth" in money or time). He'd added three official reference books to the project (a PMBOK guide and two PMP exam-prep books) and asked that they be properly consulted going forward, instead of guessing at how these calculations should work.

1. **Looked up the correct formula properly**, using the actual reference books rather than assuming. First had a research pass done across all three books to find the exact formula and definitions. Then, at Maro's specific request to "take your time and learn," went further and read the entire risk management chapter of one of the books directly, start to finish, rather than just taking a summary at face value.
2. **Found the exact mistake.** The correct formula is: EMV = Probability x Impact, where "Impact" must be a real amount of money or time (e.g. "a 65% chance of a £40,000 problem" = an EMV of £26,000) — never a normalised, unitless "severity score." The app had been letting someone directly type in the final EMV figure as if it were just another piece of information to enter, rather than something the software works out on its own from the real inputs. This is the exact same category of mistake as the earlier CPI/SPI issue: a calculated result was being treated as raw data entry.
3. **Fixed it properly.** Added two new proper input fields — "cost impact if this risk occurs" and "schedule impact if this risk occurs," in real pounds and real days — and made the app calculate the actual EMV automatically from those, the same way a spreadsheet formula would, rather than trusting a manually typed number. Also fixed the closely related "risk rating" (used for the classic risk heat-map/matrix) the same way, since it had the identical problem.
4. **Corrected the existing demo data**, since a couple of test risks created earlier had clearly wrong numbers sitting in them from before the fix (one had an EMV of £5,000,000, which was just a number typed in during testing) — recalculated them properly rather than leaving obviously wrong figures on screen.
5. **Added automated tests that check the exact textbook example** (65% chance of a £40,000 problem = £26,000) so this specific calculation can never quietly break again without a test failing.
6. **Learned more than just the one formula.** While reading the chapter properly, also picked up that a full risk register really should distinguish between "threats" (bad risks) and "opportunities" (good risks that could save time or money), and that when adding up all the risk values to work out a project's overall contingency (safety-margin) budget, opportunities should be subtracted from threats, not just added together. The app doesn't do this yet — noted as a future improvement for when a project dashboard/summary screen gets built, rather than something to bolt on right now.

End of session 8: the EMV/rating calculation is now done properly, checked against the actual reference material rather than assumed, with automated tests locking in the real textbook example. As with previous sessions, waiting on Maro to confirm it looks right in the real app before anything is committed.

2. **Split every risk into "Threat" or "Opportunity."** Not every risk is bad — some are genuinely good things that might happen (like a supplier discount). This turned out to matter more than expected: the textbook's own examples show that a good/threatening risk affects money and schedule in opposite ways from each other (a threat costs money but adds days to the schedule; an opportunity saves money but also saves days) — a subtle detail that was checked carefully against the book rather than assumed, and locked in with tests proving both directions work correctly.
3. **Added "before and after mitigation" risk ratings, with a real visual heat-map.** Previously there was only one risk rating. Now there's the "as things stand today" rating and a separate "what we're aiming for once our mitigation plan works" target rating, shown side by side on an actual colour-coded 5×5 grid (green/yellow/red), the same style of chart shown in the original demo — not just numbers in a table.
4. **Added a proper checklist of mitigation actions per risk.** Rather than one vague "mitigation status" note, each risk can now have its own numbered to-do list of specific actions (e.g. "MA-01: Dual-source supplier"), each with its own owner, due date, status, and progress bar — plus separate "if this happens, do X" and "if X doesn't work, do Y" fallback plans.
5. **Added an editable rulebook for what "High probability" or "Critical impact" actually mean.** Different people might disagree about what counts as a "Medium" risk unless it's written down somewhere shared. Added an editable table (collapsible section at the top of the Risk Register) defining exactly what each probability and impact level means in real terms (e.g. "Medium probability = 25-50% chance," "Critical impact = over £1,000,000 or over 8 weeks"), pre-filled with sensible defaults from the original demo, editable per project.
6. **Made the "how much could this cost" estimate more realistic.** Instead of a single guessed number, risks can now record a Minimum, Most Likely, and Maximum estimate for both cost and schedule impact — like asking "best case, most likely case, worst case?" instead of just one figure. The actual EMV calculation still uses only the "Most Likely" figure, deliberately — the textbook's own worked examples never blend all three into one weighted formula, so rather than invent a fancier calculation that couldn't be checked against the source material, the simpler, verifiable approach was kept.

Along the way, a genuinely large amount of new automated testing was added (26 new tests across three new test files, on top of extending the existing risk tests) — the backend test count went from 71 at the very start of today's session to 97 by the end, and every single one still passes.

**Deliberately left for later, not because they were missed but because they belong elsewhere:** working out a project's overall risk "safety margin" budget by adding up every threat and subtracting every opportunity (that's a whole-project summary, which needs a dashboard screen that doesn't exist yet), and a formal "watch list" for minor risks that don't need full tracking yet.

End of session 9: the Risk Register now reflects both the original product vision and genuine textbook-verified project-management practice, not just a working demo. ## Session 14 — 2026-07-02 (continued): The big one — hours instead of whole days, everywhere

With the go-ahead given, this session rebuilt the calendar and critical-path system from whole-day precision to hour precision — comparable in size to building the critical-path engine itself the first time round.

**What "whole days" meant before, and why it wasn't enough:** every date the system worked out (start, finish, how much spare time an activity has) was calculated one whole day at a time — a task either worked a full day or it didn't, with no concept of "this task finishes at 2pm, so the next one can start right after lunch." That's fine for a rough programme, but it meant the new calendar editor's whole point — marking a specific hour as non-working — couldn't actually change anything real.

**What changed:**

1. **Calendars now have a proper daily shape**, not just a single "hours per day" number typed in. Each calendar gets a start time and end time for its working day (e.g. 08:00 to 17:00), and can have any number of repeating daily breaks (like a 12:00-13:00 lunch) subtracted from it. The "hours per day" figure isn't typed in anymore at all — it's worked out automatically from the day's shape minus its breaks, the same "don't let people type in an answer the computer should work out" rule already applied everywhere else in this project. The very first calendar every project gets automatically comes with a sensible lunch break already set up, so the feature is visible immediately rather than starting empty.
2. **Non-working exceptions can now target part of a day, not just the whole thing.** A bank holiday still blocks the entire day as before, but now you can also say "just 08:00 to 09:00 is blocked on this one date" (e.g. a delivery causing a late start), and the rest of that day works normally.
3. **Every date in the system now carries a time, not just a day.** Duration is now typed in as hours rather than days (an activity is "40 hours" rather than "5 days"), and start/finish/actual dates/deadline dates all carry a real time of day. A "days" figure is still shown for anyone who thinks in days — it's now calculated automatically from the hours, using whichever calendar that activity is actually on, rather than being something separate that could drift out of sync.
4. **The critical-path calculator was rebuilt to think in hours.** This was the heart of the work: instead of walking forward or backward one whole day at a time, it now walks forward and backward counting actual working minutes, correctly skipping lunch breaks, non-working hours, and the new partial-day exceptions. One nice side effect: a slightly artificial rule from the old day-based version — "a task can only start the day *after* its predecessor finishes, never the same day" — went away entirely, because with real hour precision a task can now correctly start at 2pm the moment the one before it finishes at 2pm. That old rule was only ever a workaround for not being able to represent "later the same day"; once the system can represent that properly, the workaround isn't needed and the result is more accurate, not less.
5. **Spare time ("float") is now measured in hours too**, not whole days, so a task with 4 hours of slack shows that honestly instead of rounding to "0 days" or "1 day."
6. **The calendar editor screen** was rebuilt to match: instead of typing in a single "hours per day" number, you now set the day's start/end time and add named breaks (with a live-updating "net hours/day" figure that proves it's being worked out automatically). The non-working exceptions form gained an optional "only part of the day" toggle. Duration fields across the app switched to hours, and date fields that need a specific time (like actual start, actual finish, and deadline constraints) switched to proper date-and-time pickers instead of just a date.

**A genuinely interesting edge case surfaced while writing the tests**, worth recording: if a predecessor finishes exactly at Friday close of business, and a downstream deadline is set to that exact same instant, the "how far off is this deadline" (float) calculation comes out as *zero*, not negative — even though the schedule is technically impossible (the earliest the following milestone can happen is Monday morning, after the deadline). This isn't a bug: since there's genuinely no working time at all between Friday's close and Monday's open, there's nothing to measure a "distance" in — the same reasoning that lets a task correctly continue immediately after a weekend with no artificial gap. The float number only turns properly negative once the deadline and the earliest-possible time are separated by at least some real working time (e.g. the deadline is a day or two earlier still). This is a subtlety of hour-precision scheduling that didn't exist in the old day-based version, where the maths happened to always show at least one day of overrun in this situation — worth remembering if a deadline ever looks like it's "just barely" met when it shouldn't be.

**Existing data was carried across, not thrown away.** A one-time conversion changed old duration/float numbers from days to hours (using this project's long-standing 8-hours-a-day assumption), and gave existing dates a sensible default time of day rather than leaving them all blank or at midnight. The conversion can be undone cleanly if it ever needs to be (checked both directions actually run without errors).

## Session 17 — 2026-07-03: Earned Value columns in Scheduling, and three real corrections from someone who actually knows P6

Maro asked for the full Earned Value set — AC, PV, EV, CV, SV, CPI, SPI, BAC, EAC, ETC — as columns in the Scheduling table itself, not just Cost Plan. Built by reusing the exact same formulas Cost Plan already had (never a second, independently-derived copy of the maths), surfaced through each activity's linked Cost Plan line. Straightforward on paper — but this session turned into a genuine back-and-forth with Maro's real Primavera P6 planning experience, and three separate corrections along the way, each one catching something a textbook description alone wouldn't have.

**First: a duplicate-source-of-truth bug, the same class already fixed several times before in this project.** After the first version shipped, Maro reported the numbers "didn't align" between Scheduling and Cost Plan. The cause: the Cost Plan line linked to a resourced activity had its own, separately-editable "% Complete" field — completely disconnected from the activity's own % Complete in Scheduling. Whichever screen you'd actually typed a number into is the one whose Earned Value moved. Fixed by making % Complete live on the Activity alone, syncing one-way into its linked Cost Plan line automatically (and Cost Plan's own copy of the field became read-only, with a note pointing back to Scheduling) — the same "don't let two fields represent one fact" rule that's caught this exact bug shape in Risk and Cost before.

**Second, and the big one: Planned Value was anchored to the wrong date entirely.** The first build required a captured baseline before PV would show anything, and prorated against the *frozen* baseline dates. Maro corrected this directly, with a worked example: a 10-day, £100/day activity has a BAC of £1,000 regardless of progress; by the end of day one, PV should be £100, because that's how far along the *schedule* says the activity should be — using the activity's own **current, live dates**, not a separately-captured baseline. "Set Baseline" measures schedule *variance* (how far the current plan has drifted from what was originally agreed) — a completely different question from Planned Value, which just asks "given today's plan, how much should be done by now." Rebuilt PV around the activity's live start/finish, gated only on the activity being scheduled at all (near-instant) rather than needing a deliberate baseline capture. Checked against P6 and Microsoft Project's own published formulas directly — this dual-purpose gate model (PV = BAC × elapsed-fraction, computed straight off task duration + progress, no baseline required) matches how both tools actually work.

**Third: the "data date" itself was hardcoded to the real calendar date**, ignoring the fact that this project already has its own "data date" concept — the Reschedule tool's anchor (`period.start_date`), the same value the critical-path engine itself schedules from. Maro found this by testing directly: moved the data date a week forward via Reschedule, and PV didn't move. Fixed by extracting a single shared `data_date_for_period` function and threading it through everywhere PV gets computed, so Reschedule and Planned Value are finally looking at the same clock.

**That test also surfaced a deeper, correct instinct Maro had about how Reschedule itself should behave, going beyond just fixing PV's date source: an activity that already has real progress shouldn't have its Start moved by a reschedule at all.** "If there is progress then it actually started on that planned date" — once % Complete is above zero, the current Start is a recorded fact, not a forecast, and no amount of shifting the overall programme should retroactively change history. Not-yet-started work is different: it's fair game to be pulled forward if the data date moves past where it was planned to begin (the same behaviour P6 itself uses when applying a Reschedule). This meant a real change to the critical-path engine's forward pass — the most heavily-tested part of the whole codebase — so it went through a full CPM + reschedule test run (all 18 CPM tests plus 5 reschedule tests, including new ones proving the exact worked scenario) before being accepted. An in-progress activity's Finish is now driven by **Remaining Duration** — itself a value Maro pointed out was wrongly a manual input (typed in separately from Duration and % Complete, when it's just simple arithmetic: 20 days at 10% complete leaves 18 days remaining) — fixed to be computed, not typed, the same "never expose a derivable value as a manual input" rule as everywhere else.

**Smaller pieces that came out of the same conversation:** a genuine "Duration % Complete" figure now shows directly on the activity — the number PV is actually derived from, so the whole calculation is visible rather than a black box. Reschedule gained a second mode: pick an exact new data date on a calendar, instead of only "shift forward/backward by an amount" (P6 supports both; typing exact numbers of days was the harder way to do the same thing). A genuinely separate bug also turned up while building that: the Reschedule panel's own "Data Date" display went stale the moment it was closed and reopened, because the app only ever fetched the current Period once on page load and never again — fixed by giving the underlying hook a proper refetch. And Actual Cost can now be entered directly from Scheduling's Resource Assignments panel (matching how P6 captures it alongside resource assignments), rather than needing a trip to Cost Plan.

**Closed the loop by checking Cost Plan itself.** PV/EV/SV/SPI were being computed correctly server-side the whole time, but Cost Plan's own screen had never actually been updated to show them — added to the row detail panel, the CSV export, and both print views, so a QS working entirely from Cost Plan sees the exact same schedule-performance numbers Scheduling does, not a narrower view of the same data.

288 automated backend tests passing by the end (up from 281 — new coverage for the EVM columns themselves, the corrected date-anchoring, and the in-progress-activity CPM behaviour). Frontend passed a full type-check and production build with zero errors throughout. **Maro tested each fix directly in the browser as it landed** — the reschedule-pins-progress fix, the data-date picker, and the Cost Plan alignment were all confirmed working before this session's work was committed and pushed.

## Session 18 — 2026-07-03/04: A detour into Syncfusion and back out again, then a long stretch of real Scheduling polish

## Session 19 — 2026-07-04: Old projects couldn't actually be deleted — fixed properly, not just patched over

Maro noticed the "switch project" screen showed every old test project ever created, with no way to get rid of any of them, and asked for a checkbox-based way to set a project active/inactive or delete it.

Before writing anything, this needed a real decision from Maro, because "delete" turned out to hide a serious safety problem once actually checked: the app already had a working-looking `DELETE` button for a project, but almost none of the ~15 other tables that store a project's real data (its schedule, costs, risks, ICD log, resources, calendars) were wired up to actually clean themselves up when their parent project disappeared — meaning trying to delete any project with real data in it would have thrown a database error rather than doing anything. Making that genuinely safe meant touching a database migration across all those tables, and a true permanent delete is inherently irreversible — exactly the kind of call that shouldn't be made silently on Maro's behalf. He was asked directly and chose the thorough option: build both a safe, reversible "Archive" (hide a project without touching its data) **and** properly fix the permanent delete so it can be trusted too, rather than picking just one.

What got built:

1. **Every table that depends on a project (directly or several steps removed) now cleans itself up automatically when that project is deleted** — periods, activities, calendars, resources, risks and their mitigation actions, cost elements and their commitments/rate lines, ICD items and their action items/comments, criteria tables, and saved schedule baselines. Previously deleting a project with any of this real data would have failed outright with a database error.
2. **A genuine, subtle bug was found and fixed while checking this actually worked, not just assuming the database change was enough.** Simply asking the app's data layer to "delete this project" was quietly trying to blank out the project reference on child records first — before the database's own new cleanup rules got a chance to run — which failed for the same reason as before (a blank reference isn't allowed on records that must always belong to a project). Fixed by issuing a more direct "just delete it" instruction that leaves all the cleanup entirely to the database's own rules, which is what was actually intended. This was only caught by building a real test scenario — a throwaway project with a genuine activity, a resource assigned to it, a risk, and a cost line all attached — and deleting it for real against the actual project database, not just the simplified one the automated test suite normally uses.
3. **One deliberate exception, kept on purpose:** a Resource that's still assigned to an activity is normally blocked from being deleted on its own, as a safety net against accidentally losing cost data outside of a full project teardown. Deleting a whole project still needs to get past that safety net cleanly — solved by explicitly clearing out those assignments as the very first step of a project delete, before anything else runs, rather than weakening the safety net itself.
4. **The "switch project" screen now has a checkbox next to every project**, plus a small action bar that appears once anything's ticked: Set Active, Archive, or Delete. Archive/Set Active just flips the same status label already shown on each project's badge — fully reversible, no risk. Delete is gated behind a confirmation popup that names exactly which projects are about to be permanently removed and spells out that it takes their whole schedule/cost/risk/ICD history with them.

322 automated backend tests passing by the end (up from 321 — added a permanent regression test that deletes a project carrying real cross-module data, so this exact class of bug can't silently return). Frontend passed a full type-check with zero new errors. Committed and pushed at Maro's request.
